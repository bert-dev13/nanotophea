# NANOTOPHEA Bioinformatics Research Platform

## Final Redevelopment and Implementation Plan

**Project:** NANOTOPHEA / NanoHepatoTea Bioinformatics Research
Platform\
**Status:** Final redevelopment plan\
**Primary Goal:** Redevelop the current hardcoded UI prototype into a
functional, research-aligned platform that clearly separates
computational predictions, laboratory results, literature/reference
data, and researcher interpretation.

------------------------------------------------------------------------

## 1. Executive Direction

The current NANOTOPHEA application should not simply be connected to a
database while retaining its existing simulated behavior. It should be
redeveloped around the actual research workflow.

The final system should follow this scientific flow:

``` text
Research / Reference Data
        ↓
In-Silico Analysis
        ↓
Laboratory Results
        ↓
Statistical & Comparative Analysis
        ↓
Researcher Interpretation
        ↓
Research Reports / Exports
```

The most important design principle is:

> **Computational predictions support hypotheses; laboratory results
> test them.**

The system must never present simulated, predicted, or
literature-derived values as actual laboratory findings.

------------------------------------------------------------------------

## 2. Core Evidence Model

Every important scientific value stored or displayed by the system must
have an evidence classification.

  -----------------------------------------------------------------------
  Evidence Type                       Meaning
  ----------------------------------- -----------------------------------
  `PREDICTED`                         Generated by a documented
                                      computational, docking, QSAR, or
                                      predictive model

  `EXPERIMENTAL`                      Obtained from actual laboratory
                                      testing or uploaded laboratory
                                      results

  `LITERATURE`                        Taken from a cited scientific
                                      publication or trusted scientific
                                      source

  `REFERENCE`                         Scientific metadata such as PubChem
                                      CID, SMILES, PDB ID, molecular
                                      weight, etc.

  `INTERPRETATION`                    Human-authored researcher analysis
                                      or conclusion

  `SIMULATION`                        Exploratory mathematical simulation
                                      that is not a validated predictive
                                      model
  -----------------------------------------------------------------------

### Critical Rule

Do not label a generated value as `PREDICTED` unless the system can
identify the model or scientific method used to generate it.

For prediction modules, record whenever applicable:

-   Model name
-   Model version
-   Scientific method
-   Input variables
-   Dataset/training source
-   Validation information
-   Assumptions
-   Date generated
-   References

Existing Hill-equation or synthetic models without validated scientific
prediction methodology should be classified as **SIMULATION**, not AI
predictions.

-   Next.js

-   TypeScript
-   Tailwind CSS
-   Recharts
-   Existing 3D molecular visualization foundation where reusable

### Backend / Application Services

Use **Next.js Server Actions and/or Route Handlers** for normal
application operations.

redevelopment unless a future requirement clearly requires it.

### Firebase

Use Firebase as the main application backend platform.

-   Adviser/reviewer accounts if needed
-   Study ownership
-   User sessions


#### Cloud Firestore

Used for:

-   Studies
-   Formulations
-   Compounds
-   Proteins
-   Cell lines
-   Prediction/simulation runs
-   Docking records
-   Laboratory datasets
-   Laboratory replicates
-   Statistical results
-   Comparison results
-   Researcher interpretations
-   References/provenance
-   Audit metadata

#### Firebase Storage

Used for:

-   Vina logs
-   PDB/PDBQT files
-   Docking poses
-   Laboratory reports
-   HPLC reports
-   Supporting PDFs
-   Generated research exports

Firebase should store and coordinate scientific data, but heavy
scientific computation should not be forced into Firestore.

Future scientific services may use:

``` text
Python / FastAPI
├── AutoDock Vina
├── RDKit
├── Statistical analysis
└── Validated ML/QSAR models
```

For the MVP, **Vina import should be implemented before live server-side
Vina execution**.

-   Tea formulation
-   Preparation method
-   Storage information
-   Quercetin marker information

### 7.2 Phytochemicals

Retain the useful existing phytochemical structure but connect values to
real sources.

Fields may include:

-   Compound name
-   PubChem CID
-   SMILES
-   Molecular formula
-   Molecular weight
-   H-bond donor/acceptor
-   TPSA
-   LogP
-   Structure
-   Source
-   Retrieved date
-   Scientific references

Primary study compound:

**Quercetin**

Additional compounds can remain available when supported by the study.

### 7.3 Target Proteins

Store protein identity separately from docking results.

Fields:

-   Protein name
-   Gene
-   PDB ID
-   Pathway
-   Biological role
-   Source/reference

Do not store a quercetin binding affinity as a permanent property of the
protein.

Binding affinity belongs to a **Docking Run**.

### 7.4 Cell Lines

Primary study focus:

**HepG2 liver cancer cells**

Other cell lines may be included only as literature/reference context
when relevant.

Separate:

-   Literature values
-   Predicted values
-   Experimental values

Never mix them in the same field.

display them side by side.

``` text

              Computational     Experimental
IC50              —                 —
50 µg/mL          —                 —
100 µg/mL         —                 —
250 µg/mL         —                 —
500 µg/mL         —                 —

      [Comparative Dose-Response Chart]

Difference / Agreement Metrics

Researcher Interpretation:
[________________________________]
```

Possible comparison outputs:

-   Difference at each concentration
-   ΔIC50
-   Relative error where scientifically meaningful
-   Curve comparison
-   Rank/order comparison

Avoid automatic claims such as:

-   Proven
-   Validated
-   Confirmed effective

The system should present evidence and allow the researcher to interpret
it.

## 25. Definition of Done

The redevelopment is successful when:

1.  No important scientific value exists only as unexplained hardcoded
    data.
2.  Every result clearly identifies its evidence type.
3.  Laboratory results come only from real entered/imported laboratory
    data.
4.  Simulations are labeled as simulations.
5.  Predictions identify the model/method used.
6.  Docking values originate from real AutoDock Vina outputs or clearly
    identified imported outputs.
7.  Data persists through Firebase.
8.  Experimental DPPH follows the approved treatment/replicate design.
9.  Experimental LDH behavior follows the final researcher-approved
    protocol.
10. Computational and experimental data can be compared without being
    conflated.
11. Researchers---not the software---make final scientific
    interpretations.
12. Statistical outputs can be traced back to raw experimental data.
13. Reports clearly separate computational, experimental,
    literature/reference, and interpretation content.
14. Clinical dosage recommendations are absent from the research
    workflow.
15. The platform tells a coherent research story:

``` text
Research Data
      ↓
In-Silico Analysis
      ↓
Laboratory Testing
      ↓
Statistical / Comparative Analysis
      ↓
Researcher Interpretation
      ↓
Research Output
```

## Final Development Principle

> **Do not redesign NANOTOPHEA merely to make the prototype look more
> complete. Redevelop it so that every displayed result has a traceable
> scientific origin.**

defensible, reproducible, and clearly structured research workflow.
